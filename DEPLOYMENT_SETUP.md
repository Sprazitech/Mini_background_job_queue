# Deployment Setup Guide

## Overview
This guide outlines the deployment configuration for the Mini Background Job Queue application. The project uses a single-environment setup (no staging) with Supabase as the database backend.

## Environment Variables

### Production (GitHub Secrets)
Add these secrets to GitHub Repository → Settings → Secrets and variables → Actions:

| Secret Name | Value Source | Example Format |
|-------------|--------------|----------------|
| `DATABASE_URL` | Supabase Dashboard → Database → Connection String | `postgresql+asyncpg://postgres.[ref]:[PASSWORD]@aws-0-[region].pooler.supabase.com:6543/postgres` |
| `SUPABASE_URL` | Provided in M5_HANDOFF.txt | `https://apyvyinpeklkuultxwsj.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase Dashboard → Project Settings → API → Service Role Key | `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...` |
| `API_KEY` | Generated by M5 (secure random) | `prod_jobqueue_$(date +%s)_$(openssl rand -hex 12)` |

### Development Configuration
The following values are configured in `.env.example` and local `.env` files:

| Variable | Development Value | Production Default | Purpose |
|----------|------------------|-------------------|---------|
| `WORKER_ENABLED` | `false` | `true` | Enable/disable background worker |
| `WORKER_CONCURRENCY` | `1` | `1` | Number of concurrent worker processes |
| `MAX_RETRIES` | `3` | `3` | Maximum retry attempts for failed jobs |
| `RATE_LIMIT_PER_MINUTE` | `100` | `30` | API rate limiting |

## File Locations

### 1. `.env.example` (Committed to Git)
- Contains **placeholder values only**
- Template for developers to create their `.env` file
- **NEVER** add real credentials here

### 2. `.env` (Local Development - NOT committed)
- Created locally by developers
- Contains **test/development values only**
- In `.gitignore` to prevent accidental commits

### 3. GitHub Secrets (Production)
- Store **real production credentials only**
- Accessed by CI/CD pipeline
- Secure storage for sensitive data

### 4. CI/CD Configuration (`.github/workflows/ci.yml`)
- Uses **test values** for automated testing
- Connects to local PostgreSQL service in CI
- Uses mock Supabase URLs

## Setup Instructions

### For Developers (Local Setup)
1. Clone the repository
2. Run `./scripts/dev.sh` to set up virtual environment
3. Copy `.env.example` to `.env`: `cp .env.example .env`
4. Edit `.env` with local development values
5. Start development server: `uvicorn app.main:app --reload --port 8000`

### For M5 (Production Setup)
1. Get Supabase credentials from project admin
2. Generate secure API key: `openssl rand -base64 48`
3. Add all secrets to GitHub Repository Secrets
4. Verify production configuration

### For CI/CD (Automated Testing)
- Already configured in `ci.yml`
- Uses PostgreSQL service in GitHub Actions
- Tests run with mock environment variables

## Security Guidelines

### 🔐 NEVER Commit:
- Real database credentials
- Service role keys
- Production API keys
- Any sensitive data

### ✅ ALWAYS Do:
- Use different keys for development vs production
- Store production secrets in GitHub Secrets only
- Use `.env` for local development (in `.gitignore`)
- Rotate keys if compromised

##### Key Generation

### Production API Key
```bash
# Generate secure random key (64 characters)
openssl rand -base64 48

# Alternative: Python
python -c "import secrets; print(secrets.token_urlsafe(36))"
```

### Development API Key
Use simple memorable value: `dev-key-change-me` or create your own.

## Troubleshooting

### Common Issues:
1. **Connection refused**: Verify database is running locally
2. **Authentication failed**: Check `.env` values match Supabase credentials
3. **Rate limiting**: Adjust `RATE_LIMIT_PER_MINUTE` in `.env`
4. **Worker not starting**: Set `WORKER_ENABLED=true`

### Verification Steps:
1. Test local setup: `./scripts/dev.sh`
2. Verify CI passes: Check GitHub Actions
3. Test production connection: Use real credentials in secure environment

## Maintenance

### Regular Tasks:
- Rotate API keys periodically
- Update dependencies in `requirements.txt`
- Review security checklist in `SECURITY.md`
- Backup database regularly

### Emergency Procedures:
1. Compromised key: Generate new key and update all locations
2. Database breach: Reset all credentials
3. Deployment failure: Check GitHub Secrets and environment variables

## Render service settings

For the Render web service, use the following commands:

- **Build command:** `pip install -r requirements.txt`
- **Start command:** `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- **Runtime:** Python

The command must be `uvicorn`, not `unicorn`. The project includes the `uvicorn[standard]` dependency; there is no `unicorn` executable.

The repository contains `.python-version` with Python `3.12`. After the file is merged into the branch configured in Render, use **Clear build cache & deploy**. Alternatively, set the Render service environment variable `PYTHON_VERSION` to a fully qualified Python 3.12 release.

## Database URL and frontend environment variables

### Render backend

Set `DATABASE_URL` to the Supabase session-pooler connection string. The preferred format is:

```text
postgresql+asyncpg://USER:PASSWORD@HOST:PORT/DATABASE
```

The backend now normalizes `postgresql://` and `postgres://` values to the asyncpg dialect as a safety measure. Do not add `psycopg2` just to work around a synchronous URL; this application uses SQLAlchemy's async engine and `asyncpg`.

Render must also contain these backend variables:

```text
DATABASE_URL
SUPABASE_URL
SUPABASE_SERVICE_ROLE_KEY
API_KEY
WORKER_ENABLED=true
WORKER_CONCURRENCY=1
MAX_RETRIES=3
RATE_LIMIT_PER_MINUTE=30
```

### Vercel frontend

The current frontend is static HTML/CSS/JavaScript and does not require backend secrets in Vercel. Do **not** add `DATABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, or the private backend `API_KEY` to Vercel.

The API origin is currently configured in `docs/index.html` through the `api-base` meta tag. Update that value only if the Render service URL changes. The browser asks the user for an API key and keeps it in session storage; this is suitable only for controlled MVP testing, not secure public authentication.


## SMTP email provider configuration

The `send_email` worker now sends through an SMTP-compatible provider. Configure
these variables in Render only; do not put SMTP credentials in Vercel or commit
them to Git:

```text
SMTP_HOST=smtp.provider.example
SMTP_PORT=587
SMTP_USERNAME=provider-username
SMTP_PASSWORD=provider-password
EMAIL_FROM=verified-sender@example.com
SMTP_USE_TLS=true
SMTP_USE_SSL=false
```

Use either STARTTLS (`SMTP_USE_TLS=true`, normally port 587) or implicit TLS
(`SMTP_USE_SSL=true`, normally port 465), not both. The provider must authorize
`EMAIL_FROM`. A missing SMTP configuration causes send_email jobs to fail clearly
and enter the normal retry/DLQ path instead of reporting simulated success.

After adding the variables to Render, redeploy the service and test with a
recipient address you control. Never place these credentials in Vercel, the
frontend, `.env.example`, logs, or chat.


## Resend HTTPS email testing on Render Free

Render Free blocks outbound SMTP ports, so use Resend's HTTPS API instead of
SMTP for the deployed worker. Add these variables to Render:

```text
RESEND_API_KEY=re_your_resend_api_key
EMAIL_FROM=onboarding@resend.dev
```

The `onboarding@resend.dev` sender is for testing and is restricted by Resend to
the email address associated with the Resend account. To send to other
recipients, verify a custom sending domain and set `EMAIL_FROM` to a sender at
that domain. Do not put `RESEND_API_KEY` in Vercel or the frontend.

When `RESEND_API_KEY` is present, the worker uses the Resend HTTPS API. SMTP is
used only when Resend is not configured and is not suitable for a Render Free
service.


## Protected production deployment workflow

The production workflow requires the GitHub `production` Environment approval and
these GitHub Actions secrets:

```text
RENDER_DEPLOY_HOOK_URL
VERCEL_DEPLOY_HOOK_URL
```

M5 must configure required reviewers for the `production` Environment in GitHub
Settings before production deployments can proceed. Deployment hook URLs are
secrets and must not be logged or shared.
